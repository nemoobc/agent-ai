# Product & UX

## When to use
Define requirements, design user flows, make UX decisions, structure information architecture. Practical over aspirational.

## Key rules
- Write requirements as testable acceptance criteria, not vague goals
- Map user flows before implementing; identify edge cases early
- Optimize for the common path; handle errors gracefully at edges
- Use real user data and feedback, not assumptions
- Prefer incremental delivery over big-bang launches

## Anti-patterns
- Don't design for the 1% edge case at the expense of the 99%
- Don't add features without clear user need
- Don't confuse "more options" with "better UX"
